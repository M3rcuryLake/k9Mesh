# K9MESH GCS — Live Telemetry Verification Manual

## 1. Purpose

This manual describes how to verify the K9MESH Ground Control Station's live telemetry pipeline before connecting the physical rover.

The verification process checks three things independently:

1. **WebSocket listener** — Is K9MESH listening on `127.0.0.1:8080`?
2. **Backend producer** — Is the backend/emulator generating and transmitting telemetry?
3. **Packet reception** — Is K9MESH actually receiving, parsing, validating, and displaying the packets?

The intended telemetry path is:

```text
Backend / Sensors
      │
      ▼
JSON Telemetry
      │
      ▼
WebSocket 127.0.0.1:8080
      │
      ▼
K9MESH Electron
      │
      ├── JSON Parser
      ├── CSI Adapter
      ├── Validator
      └── Telemetry Host
              │
              ▼
          React UI
```

---

# 2. Prerequisites

Before starting:

* K9MESH repository is available locally.
* Node.js/npm are installed.
* Python is installed.
* Python `websockets` package is installed.
* No other application should be using port `8080`.

Check Python:

```powershell
python --version
```

Check the WebSocket Python package:

```powershell
python -c "import websockets; print('websockets OK')"
```

Expected:

```text
websockets OK
```

---

# 3. Check Whether Port 8080 Is Available

Before starting K9MESH, check whether another process already owns port `8080`.

Run:

```powershell
netstat -ano | findstr :8080
```

### If nothing is returned

Port `8080` is currently free.

Proceed to start K9MESH.

### If something is returned

Example:

```text
TCP    127.0.0.1:8080    0.0.0.0:0    LISTENING    12345
```

The final number is the process ID (PID).

Identify it:

```powershell
tasklist /FI "PID eq 12345"
```

If it is an old K9MESH/Electron/Node process that should no longer be running, terminate it:

```powershell
Stop-Process -Id 12345 -Force
```

Then check again:

```powershell
netstat -ano | findstr :8080
```

---

# 4. Start the K9MESH WebSocket Listener

Open **Terminal 1** in the K9MESH project directory.

For a live integration test:

```powershell
npm run integration:test
```

For detailed telemetry diagnostics:

```powershell
$env:DEBUG_TELEMETRY="1"
npm run integration:test
```

K9MESH should start and eventually report:

```text
[WS] Listening on ws://127.0.0.1:8080
[WS] Waiting for producer...
```

## What this means

This is a successful listener state.

It means:

```text
Electron started
      ↓
TelemetryHost initialized
      ↓
WebSocketTelemetrySource initialized
      ↓
127.0.0.1:8080 successfully bound
      ↓
Waiting for backend
```

At this point **the backend has not connected yet**.

That is normal.

---

# 5. Independently Confirm the Listener

While K9MESH is showing:

```text
[WS] Waiting for producer...
```

open another PowerShell window and run:

```powershell
netstat -ano | findstr :8080
```

You should see something similar to:

```text
TCP    127.0.0.1:8080    0.0.0.0:0    LISTENING    <PID>
```

This confirms that Windows has an active process listening on port `8080`.

You can identify the process:

```powershell
tasklist /FI "PID eq <PID>"
```

It should correspond to the K9MESH/Electron process.

---

# 6. Start the Backend Emulator

Once K9MESH says:

```text
[WS] Listening on ws://127.0.0.1:8080
[WS] Waiting for producer...
```

open **Terminal 2**.

Run:

```powershell
python scratch/test_live_backend.py --demo
```

The test producer should connect to:

```text
ws://127.0.0.1:8080
```

You should see something similar to:

```text
[TEST-BACKEND] Connected to ws://127.0.0.1:8080
[TEST-BACKEND] DEMO STATE 1
```

The producer is now acting as the external telemetry backend.

---

# 7. Confirm K9MESH Received the Connection

Return to Terminal 1.

The previous:

```text
[WS] Waiting for producer...
```

should change to something similar to:

```text
[WS] Producer connected from 127.0.0.1
```

This proves:

```text
Python backend
       ↓
WebSocket connection
       ↓
K9MESH :8080
```

is working.

---

# 8. Confirm Packets Are Being Received

With:

```powershell
$env:DEBUG_TELEMETRY="1"
```

enabled, K9MESH should provide detailed pipeline information.

You should see events similar to:

```text
[WS] Packet received
[Parser] JSON parsed
[Adapter] Packet normalized
[Validator] Packet accepted
[Host] Telemetry published
[IPC] Telemetry dispatched
```

This is the important sequence.

It establishes that the packet isn't merely reaching the socket.

It is going through the complete telemetry pipeline.

---

# 9. Confirm the Actual JSON

The test producer should report its transmitted values.

For example:

```text
[TEST-BACKEND] DEMO STATE 1
rssi=-61
channel=5
variance=0.0010
confidence=25.0
```

The corresponding K9MESH UI should display those values.

For example:

```text
RSSI       -61 dBm
CHANNEL    5
CONFIDENCE 25.0000000000%
```

The exact UI location depends on the current K9MESH layout.

The test producer's `--demo` mode deliberately changes values.

For example:

### State 1

```text
RSSI       -61
CHANNEL    5
VARIANCE   0.0010
CONFIDENCE 25.0
```

### State 2

```text
RSSI       -40

VARIANCE   0.0080
```

### State 3

```text
RSSI       -75
```

### State 4

```text
VARIANCE   0.0030
```

These changes should appear in the K9MESH UI **without restarting the application**.

This is the strongest manual test that the frontend is actually consuming live telemetry.

# 11. Verify the Motion Graph

The current backend packet contains:

```json
"mvs": {
    "state": "motion",
    "variance": 0.0002945,
    "threshold": 0.0001771,
    "confidence": 83.1163
}
```

The Motion Detection panel should therefore react to changes in:

```text
mvs.variance
mvs.threshold
```

When the producer changes those values, the graph should change accordingly.

No graph values should be generated independently by React.

---

# 12. Verify Missing Telemetry

The test packet does **not necessarily contain every rover sensor field**.

For example, if the backend doesn't provide:

```text
Battery
GPS
IMU
Odometry
Breathing rate
STM32 telemetry
```

the UI should **not invent values**.

It should show the application's unavailable representation:

```text
--
N/A
NO FIX
AWAITING SIGNAL
```

depending on the widget.

This is intentional.

---

# 13. Test Backend Disconnect

While the test producer is running, press:

```text
Ctrl+C
```

in Terminal 2.

K9MESH should detect:

```text
[WS] Producer disconnected
```

The Electron application itself should remain running.

The WebSocket server should continue listening.

Verify:

```powershell
netstat -ano | findstr :8080
```

Port `8080` should still be listening.

### Important

K9MESH must **not revert to mock/scenario telemetry** merely because the backend disconnected.

---

# 14. Test Backend Reconnection

Restart the producer:

```powershell
python scratch/test_live_backend.py --demo
```

K9MESH should again report:

```text
[WS] Producer connected from 127.0.0.1
```

and telemetry should resume.

The UI should begin changing again.

# 15. Troubleshooting

## `EADDRINUSE`

```text
listen EADDRINUSE: address already in use 127.0.0.1:8080
```

Something already owns port `8080`.

Run:

```powershell
netstat -ano | findstr :8080
```

Identify the PID and determine what process owns it.

**Do not start another WebSocket server on port 8080.**

K9MESH is the WebSocket **server**.

The backend is the WebSocket **client/producer**.

---

## K9MESH says "Waiting for producer" forever

Check:

1. K9MESH is listening on `127.0.0.1:8080`.
2. Python producer is actually running.
3. Producer is connecting to exactly:

```text
ws://127.0.0.1:8080
```

4. No firewall/application is blocking the connection.
5. The Python terminal doesn't show a connection error.

---

## Python cannot connect

Check:

```powershell
netstat -ano | findstr :8080
```

K9MESH must be listening first.

Start K9MESH **before** starting the producer.

---

## Packets connect but UI doesn't change

Enable debug mode:

```powershell
$env:DEBUG_TELEMETRY="1"
npm run integration:test
```

Then determine the last successful stage:

```text
[WS] Packet received
        ↓
[Parser] JSON parsed
        ↓
[Adapter] Packet normalized
        ↓
[Validator] Packet accepted
        ↓
[Host] Telemetry published
        ↓
[IPC] Telemetry dispatched
        ↓
React UI
```

The first missing stage identifies where to investigate.

# 16. Quick Verification Checklist

For a fast pre-demo check:

```text
[ ] Port 8080 is free before starting K9MESH
[ ] K9MESH starts successfully
[ ] [WS] Listening on 127.0.0.1:8080
[ ] [WS] Waiting for producer
[ ] netstat confirms LISTENING
[ ] Python backend starts
[ ] Python connects to 127.0.0.1:8080
[ ] [WS] Producer connected
[ ] Packets are received
[ ] JSON is parsed
[ ] Packets are adapted
[ ] Packets are validated
[ ] Telemetry is published
[ ] UI values change
[ ] Motion graph responds
[ ] Missing telemetry remains unavailable
[ ] Backend disconnect tested
[ ] K9MESH remains alive
[ ] Backend reconnect tested
[ ] UI resumes live updates
```

## The one-line mental model

When troubleshooting, think:

> **"Is K9MESH listening? Is the backend connected? Is a packet arriving? Is it being accepted? Is the UI changing?"**

Those five questions let you isolate almost every failure in the current live telemetry path without changing any code.
